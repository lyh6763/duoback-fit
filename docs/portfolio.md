# DUOBACK Fit

> 키와 체중, 앉는 습관을 알려주면 내 몸에 맞는 의자와 그 이유를 보여주는 의자 쇼룸 사이트

![홈 화면](screenshots/home.webp)

## 개요

- **기간:** 2026.10.01 – 2026.10.15 (2주)
- **구성:** 개인 프로젝트
- **역할:** 기획 방향, 디자인 콘셉트 선택, 기능 범위와 설계안 결정, 결과 검토
- **AI 활용:** 기획 문서 작성과 구현은 AI 코딩 도구 Claude Code와 협업했습니다. 저는 무엇을 만들지와 어떤 안을 택할지를 정하고, 근거가 되는 측정 결과를 확인한 뒤 다음 단계를 지시했습니다.
- **링크:** [배포 사이트](https://duoback-fit.vercel.app) · [GitHub](https://github.com/lyh6763/duoback-fit) · [기획 문서](README.md)

## 기획 배경

예전에 만든 의자 쇼핑몰(React SPA)은 일반 쇼핑몰 화면을 옮긴 수준에 머물러 있었습니다. 고칠 부분을 검토하다가, 기존 코드를 고치기보다 기획부터 다시 설계하기로 했습니다.

의자 스펙은 "좌판 높이 420–520mm, 최대 하중 120kg"처럼 의자 기준으로 쓰여 있습니다. 사용자는 이 숫자가 **내 몸에 맞는지** 판단할 수 없고, 결국 "매장에 가서 앉아봐야 안다"로 끝납니다.
그래서 목표를 "내 몸 기준으로 의자를 고른다"로 정했습니다. 몸 정보로 추천하고, 이유를 설명하고, 비교한 뒤, 직접 앉아볼 매장까지 하나의 흐름으로 잇는 것입니다. 구매 기능은 범위에서 뺐습니다.

## 주요 기능

1. **Fit Finder:** 질문 6개(1분)로 권장 좌판 높이를 계산하고(`키 × 2.5 + 25`), 모델마다 100점 만점의 적합도와 근거 체크리스트를 보여줍니다.
2. **계산식 공개:** 점수를 체형 40 · 사용 패턴 25 · 불편 부위 25 · 예산 10으로 나누어 보여주고, 계산식과 한계를 별도 페이지에 공개합니다. 같은 답변이면 항상 같은 결과가 나옵니다.
3. **몸 기준 스펙과 "나와의 핏":** 스펙 옆에 "키 158\~198cm에 적합"처럼 사람 기준 해석을 붙이고, 저장된 프로필로 목록·상세·비교 화면에 적합도를 표시합니다. 목록에서는 "내 몸에 맞는 의자만" 볼 수 있습니다.
4. **비교와 매장 연결:** 최대 3개 모델을 나란히 비교하고, 1순위 모델을 전시한 매장으로 안내합니다.
5. **개인정보를 지키는 결과 공유:** 키와 체중을 5cm·10kg 구간으로만 담은 링크로 결과를 공유합니다. 입력값은 브라우저에만 저장하고 언제든 지울 수 있습니다.

## 기술 스택

| 기술 | 선택 이유 |
|---|---|
| Next.js 16 (App Router) · TypeScript | 상품 페이지를 정적으로 생성해 검색에 노출하고, 개인화 영역만 클라이언트에서 그리기 위해 |
| Tailwind CSS v4 | 디자인 스펙의 토큰을 `@theme`으로 1:1 옮겨 스펙과 코드를 같은 이름으로 관리하기 위해 |

| GitHub Actions · Vercel | 모든 PR에서 테스트와 Lighthouse 기준을 통과해야 머지되도록 하고, 머지되면 자동 배포하기 위해 |

## 문제 해결

### 1. 성능 점수가 오르지 않은 원인을 측정으로 찾기

- **문제:** 처음 운영 사이트를 측정하니 Lighthouse 모바일 성능이 74\~81점이었습니다. 글꼴을 자체 호스팅하고, 이미지를 AVIF로 바꾸고, 클라이언트 JS를 줄여도(라우트당 171KB → 150KB, gzip) 페이지별 77\~89점에 머물렀습니다.
- **시도:** 가장 느린 페이지(77점)를 분석했습니다. 코드보다 리소스를 의심해 **Pretendard 글꼴 요청만 막고** 다시 측정하자 96\~97점이 나왔습니다. 원인은 동적 서브셋 방식이었습니다. 페이지마다 글꼴 조각 10\~15개(250\~380KB)를 레이아웃을 마친 뒤에야 요청해서 첫 화면이 글꼴을 기다렸습니다.
- **해결:** 빌드 결과물에서 실제로 화면에 나오는 글자만 모아 글꼴 파일 하나(약 82KB)로 만들고, preload와 `font-display: optional`을 적용했습니다. 문구를 바꿔 글자가 빠지면 CI가 실패하게 했고, 이후 새 문구를 넣을 때 실제로 이 검사가 빠진 글자를 잡아냈습니다.
- **측정 환경 문제:** 이후 로컬 측정값이 크게 흔들렸습니다. Lighthouse가 기록하는 CPU 성능 점수를 확인해 보니, 같은 PC에서도 백그라운드 앱 때문에 측정마다 900\~3,600 사이를 오가고 있었습니다. 그래서 측정을 GitHub Actions로 옮겨 환경을 고정하고(CPU 성능 점수 2,250\~2,450), 성능 90점 미만이면 머지를 막는 필수 검사로 만들었습니다.
- **배운 점:** 최적화를 추측으로 하지 않고, 원인 하나를 분리해 확인하는 실험을 먼저 하는 것이 가장 빨랐습니다. 측정값을 믿기 전에 측정 환경부터 검증해야 한다는 것도 배웠습니다.

### 2. 결과 공유 링크에서 키가 새는 문제 막기

- **문제:** PRD에서는 공유 링크에 원래 값 대신 구간(키 5cm, 체중 10kg)만 담기로 했습니다. 그런데 받은 쪽은 구간으로 다시 계산해야 해서 원래 결과와 달라질 수 있었습니다.
- **시도:** 약 17만 개 입력 조합으로 대표값별 결과를 비교했습니다. 기획 예시처럼 구간 하한값을 쓰면 1순위 일치율이 82.8%에 그쳤고, 키는 중앙값·체중은 상한값을 쓰면 97.1%였습니다. 체중 상한값은 실제 체중이 구간 어디에 있든 하중을 넘는 의자를 추천하지 않는다는 장점도 있었습니다.
- **추가로 찾은 문제:** 측정하는 과정에서, 공유 화면에 정확한 권장 좌판 높이(455mm)를 보여주면 계산식을 거꾸로 풀어 키(172cm)를 알아낼 수 있다는 점을 발견했습니다.
- **해결:** 공유 화면에서는 좌판 높이를 범위(450\~460mm)로만 보여주고, 원래 값을 직접 넣은 조작 링크는 거부합니다. 보는 사람의 저장된 프로필은 건드리지 않습니다. 대표값 선택이 바뀌어 일치율이 95% 아래로 떨어지면 실패하는 테스트로 이 결정을 고정했습니다.
- **배운 점:** 개인정보 보호는 무엇을 저장하느냐뿐 아니라, 화면에 보이는 값에서 무엇을 거꾸로 알아낼 수 있느냐까지 따져야 한다는 것을 배웠습니다.

### 3. 자동 검사로 실제 문제를 잡기

- 접근성 점수가 98점이었던 원인을 찾아보니, 카드 제목이 `h1` 다음에 `h2` 없이 바로 `h3`로 쓰여 있었습니다. 기존 axe 검사는 심각도가 높은 위반만 보고 있어서 이 규칙을 놓쳤습니다. 문제를 고치고 검사를 보강해, 수정 전 코드에서는 실제로 실패하는 것까지 확인했습니다.
- 공유 화면을 axe 검사에 추가하자, 베이지 배경 위 회색 안내문의 명도 대비(4.37:1)가 기준(4.5:1)에 못 미친다는 것이 드러났습니다. 고친 뒤 이 조합을 UI 스펙에 금지 규칙으로 적었습니다.
- "내 몸에 맞는 의자만" 필터는 카드에 보이는 적합 범위와 같은 함수로 판정해서, 화면에 맞는다고 적힌 의자가 필터에서 빠지지 않게 했습니다.
